# Stock iOS metric compatibility

**STOCK STATS ACCEPTANCE: BLOCKED.** The current Hub treats a successful GetData reply as a complete system snapshot. Stock iOS volume capacity for important usage is scoped to the app's directory and may include reclaimable storage. It cannot supply the existing whole-system disk contract. CPU and Darwin VM probes are implemented for local diagnostics, with stock sandbox execution deferred.

## Wire and persistence

- CBOR uses integer map keys for [Stats, Info, Details and CombinedData](../internal/entities/system/system.go). Omission means there is no key in the map. The decoder has no required-key check for these structures. The [request manager](../internal/hub/ws/request_manager.go) matches response IDs and [the WebSocket handler](../internal/hub/ws/ws.go) reads the error envelope before decoding data.
- A missing numeric key or CBOR null leaves a non-pointer numeric field unchanged. That means zero in a fresh destination and potentially a **stale prior value** in the reused `sys.data` destination on the generic WebSocket path. An explicit zero replaces the prior sample with zero. The [legacy response path](../internal/hub/transport/transport.go) copies a newly decoded struct. [TestStockEmbeddedActualHubCBORPresence](../internal/hub/stock_embedded_test.go) checks these cases and shows a legacy Hub ignores an unknown extension field.
- [System.update and createRecords](../internal/hub/systems/system.go) migrate legacy fields, then write `system_stats.stats` (type `1m`) and `systems.info` in a transaction with `SaveNoValidate`. PocketBase stores JSON blobs and does not validate each metric or infer availability. CPU, memory and root disk values persist independently in Stats and Info. The Hub neither computes the three latest percentages from capacity data nor verifies they agree. The same path writes optional `system_details` and sets the system up. Go JSON has no numeric representation for NaN or infinity, and allowing negatives or sentinels would give the calculations and UI a numeric reading.
- [Record rollups](../internal/records/records.go) decode typed JSON, sum core fields and divide by record count. Missing or null JSON members become zero in a fresh scalar. Falsely reporting zero depresses averages and can mask peaks. [Alerts](../internal/alerts/alerts_system.go) use latest Info CPU, memory and disk percent. Historical windows use Stats CPU, memory percent and maximum disk percent across the root, extra filesystems and eligible pools. Zeros can suppress or prematurely clear threshold alerts. The code skips absent representative batteries and missing CPU breakdown components, with separate handling for temperature.
- [CPU](../internal/site/src/components/routes/system/charts/cpu-charts.tsx) and [memory charts](../internal/site/src/components/routes/system/charts/memory-charts.tsx) pass missing/null scalar accessor values to [Recharts](../internal/site/src/components/charts/area-chart.tsx), which renders gaps for ordinary unstacked series. A numeric zero is plotted at the baseline. Memory uses stacked series, which can coalesce missing stack contributions into zero. [Disk](../internal/site/src/components/routes/system/charts/disk-charts.tsx) explicitly uses `du ?? 0` and has equivalent fallbacks for extra filesystems and I/O. [Overview meters](../internal/site/src/components/systems-table/systems-table-columns.tsx) use truthiness for CPU, memory and disk percent, so missing, null and valid zero render alike there even though the stored value and alerts differ.
- A GetData error prevents persistence for that poll. The current Hub closes the WebSocket on the error, tries its existing SSH fallback and can mark the system down. The embedded Agent never opens SSH and can authenticate again on reconnect. This is a connectivity demonstration with no accepted stock samples. The [disposable Hub test](../internal/hub/stock_embedded_test.go) checks zero rows for the stock error and separately proves the false-zero persistence behavior with a synthetic successful reply.

## Owner decision and migration proposal

Approve a versioned **partial GetData** option only if the product should persist battery and other scoped stock metrics independently of whole-system CPU, memory, disk and network. This is a proposal. Production Hub protocol, database and consumers have received zero implementation changes.

1. Reserve a new CBOR `DataRequestOptions` key for the Hub to advertise a partial-stats version. Use a single new reply field for versioned measurements with explicit presence and fixed scopes/units per metric ID. The extension carries measured values only. A missing ID is unavailable for that sample. A present numeric zero is a valid value. Never include an incomplete successful legacy Stats/Info payload. The stock Agent returns the existing GetData error whenever the peer has not opted in.
2. A new Hub must decode into a fresh destination, require matching negotiated version, bound lists and validate the known IDs, scopes, units, finite ranges and dependent fields before saving. Legacy Agents continue through existing decode and persistence. An older Hub continues to authenticate and gets the existing error. A new Hub may handle an opted-in, validated partial response as reachable even if the set is empty. Save no stats row for an empty set and clear the live availability of previously measured fields.
3. Use existing JSON blobs for presence-aware partial records, with an explicit format/version discriminator in Stats and Info JSON. Older stored rows retain legacy interpretation. The new Hub must read both forms. Any deployment with older readers or rollback writers needs a reader-first rollout or a separate versioned storage location. No SQL migration is proposed if all old readers are removed before enabling writes. Legacy root-disk JSON keys remain reserved for root-disk semantics. App-capacity telemetry is outside this proposal under the current privacy reason.
4. Rollups keep separate denominators for each measured series and retain valid zero values. A window with no measurement stays absent. Overview renders unavailable distinctly from 0. Charts render gaps, including stacked and disk series. Missing measurements neither trigger nor clear metric alerts. Historical windows must enforce valid-sample coverage, with reachability handled separately. Agreement on the alert coverage rule is part of approval.

Synthetic regression vectors for an approved implementation:

| Input | Required result |
| --- | --- |
| Old Hub requests GetData from stock Agent | Existing response error, no partial record |
| Legacy Agent returns complete fixture | Identical persisted JSON, rollups, charts and alerts |
| Negotiated response with battery 0, CPU/memory/disk absent | Battery zero persists and plots; no CPU/memory/disk keys; no recovery alert from absence |
| Next sample battery absent, then 80 | Live availability clears on the second poll. Historical mean over valid samples is 40, with a gap between 0 and 80 |
| Previous CPU 71, new response omits it | No prior-value reuse; live CPU unavailable and chart gap |
| Unknown version, NaN, wrong unit, duplicate IDs, invalid dependent fields | Reject before committing; legacy numeric fields are never synthesized |
| Same synthetic partial data sent as successful response to the legacy decoder | Legacy filtering/persistence is unsafe. Current executable tests pin zero and stale-value behavior |

Approval is required for the wire allocation, JSON format and rollout, chart and alert changes, and each new off-device metric scope. The first proposed persisted field is the existing representative battery tuple with presence retained. Its end-to-end acceptance test requires authorized native execution and a disposable Hub.
